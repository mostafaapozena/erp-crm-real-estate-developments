# Data Model Conventions

Conventions every collection and document follows. Implements ADR-0007 (money), ADR-0008 (time), and
ADR-0009 (record lifecycle).

## 1. Identifiers

| Kind | Purpose | Rules |
|---|---|---|
| Technical ID | Database identity, foreign references | MongoDB `ObjectId`. Never shown to users, never used in a document number. |
| Business number | Human-facing document identity | Generated by CORE-DOC from a configured sequence. Format per document type, project, and fiscal year. |
| Correlation ID | Request and job tracing | Propagated across API, worker, logs, audit, and provider calls. |
| Idempotency key | Duplicate-submission protection | Client-supplied for mutating operations; stored with its outcome. |
| Provider ID | External object reference | Stored alongside the internal ID, with a unique index. |

**Business numbers are never reused**, including after cancellation ([ADR-0009](../decisions/adr-0009-no-hard-delete.md)).
A gap in a sequence is normal and acceptable; a reused number destroys the audit trail. Sequence
generation must be atomic — two concurrent reservations must not receive the same number, which means a
find-then-increment pattern is not acceptable. Format is blocked on `SD-10`.

## 2. Standard document fields

Every business document carries:

```
_id, createdAt, createdBy, updatedAt, updatedBy, version,
legalEntityId, branchId?, projectId?, costCenterId?,   // scope anchors
status, statusChangedAt, statusChangedBy
```

Scope anchors are **denormalized onto the document** rather than resolved through joins. Data-scope
filtering happens in every query ([security-model.md](security-model.md)); requiring a `$lookup` to
evaluate a scope makes correct scoping expensive, and expensive safety gets bypassed.

## 3. Money

Per [ADR-0007](../decisions/adr-0007-decimal-safe-money.md):

```
{ amount: Decimal128, currency: "EGP" }     // storage
{ amount: "1500000.00", currency: "EGP" }   // API — string, never a JSON number
```

- Never a JavaScript `number`, anywhere, at any layer.
- An amount without a currency is invalid.
- Arithmetic uses a decimal library; `+ - * /` on money is prohibited.
- Rounding states its scale and mode explicitly at every site.
- **Allocation must be exact:** parts sum to the total, with the final part absorbing the remainder.
  Tested against values that do not divide evenly — 7, 11, and 96 instalments.
- Percentages (discount, penalty, tax, retention, commission rates) are decimals too.

## 4. Dates and times

Per [ADR-0008](../decisions/adr-0008-utc-storage-and-display-timezone.md) — two distinct types:

| Type | Use | Storage |
|---|---|---|
| `Instant` | created, approved, published, logged in, sent | UTC timestamp |
| `BusinessDate` | due date, contract date, maturity, accounting period, attendance day | Date-only, no time, no zone |

Storing a due date as a timestamp is the defect this separation prevents: a due date that shifts by a day
across a timezone boundary changes penalty liability. Distinct TypeScript types in `packages/contracts/`
make the wrong choice a typecheck failure.

## 5. Status machines

Every stateful entity declares its states and permitted transitions **as data**, not as scattered `if`
statements.

- Transitions are validated centrally. An invalid transition is rejected, not silently ignored.
- Every transition writes an audit record with actor, reason where required, and timestamp.
- Transitions affecting inventory or money occur inside a transaction.
- Status values are stable machine codes (`AWAITING_BUDGET_APPROVAL`); the UI localizes them
  ([ADR-0003](../decisions/adr-0003-arabic-first-localization.md)). A status is never stored as a
  display label in either language.

Known state machines and their blocking decisions:

| Entity | Blocked on |
|---|---|
| Unit status | `SD-03` — includes resolving the `موقوفة` ambiguity (conflict `C-06`) |
| Check / promissory note custody | `SD-07` — gap `G-06`; must be append-only movements, never overwrites |
| Campaign approval workflow | `SD-02` (approver roles and thresholds); scope approved under `SD-14` |
| Contract lifecycle | `SD-05` |
| Financial period | `SD-08` — gap `G-04`, opening requires approval |

## 6. Concurrency

Two distinct mechanisms for two distinct problems:

### Optimistic concurrency — for edits

Every document carries a `version`. An update asserts the expected version and fails with `409` if it
changed. This prevents the lost-update problem where two users load a record, both edit, and the second
save silently discards the first.

### Distributed locks — for scarce-resource contention

Redis locks where two operations genuinely compete for one resource — most importantly **unit holds and
reservations**. MASTER-MAPPING §9.3 requires atomic unit status changes, and §9 forbids double booking.

A lock is used only where justified, always with a timeout and always released in a `finally` path. A lock
is not a substitute for a transaction, and a transaction is not a substitute for a lock: the transaction
guarantees atomicity of the write, the lock prevents two transactions from both believing the unit is
available.

## 7. Transactions

Required for any multi-document state change where a partial result would be wrong:

| Operation | Must be atomic across |
|---|---|
| Unit hold and reservation | Unit status, hold record, history |
| Contract activation | Contract, unit status, installment schedule, accounting effects |
| Payment allocation | Receipt, installment allocations, customer balance |
| Accounting posting | All journal lines — a half-posted entry does not balance |
| Cancellation | Contract, unit release, refund, commission reversal, custody return |
| Payroll run | All employee records and the resulting posting |

**Transactions require a MongoDB replica set.** A standalone `mongod` silently cannot provide them, which
is why no row above can be verified until the approved Atlas development cluster is provisioned
([ADR-0018](../decisions/adr-0018-development-infrastructure-selection.md)). See
[environments.md](environments.md).

## 8. Idempotency

Anything retryable must be safe to run twice — because it will be.

| Source | Mechanism |
|---|---|
| Client mutations | Client-supplied idempotency key, stored with its outcome; a repeat returns the original result rather than acting again |
| Provider webhooks | Provider event ID stored with a unique index; duplicates acknowledged and discarded |
| Queue jobs | Deterministic job IDs; handlers check for an existing effect before creating one |
| Reminders | One send per installment per reminder type; suppressed once payment is confirmed |
| Accounting posting | Source document reference plus posting type is unique — a document cannot post twice |

Providers retry by design, so duplicate delivery is expected operation, not an error condition.

## 9. Soft state

Per [ADR-0009](../decisions/adr-0009-no-hard-delete.md), records are cancelled, archived, or deactivated —
never hard-deleted.

Consequences for queries:

1. **Repository defaults exclude** cancelled, archived, and inactive records. Including them is explicit.
   The opposite default means users eventually see superseded data in a list they trusted.
2. **Unique indexes must be partial**, scoped to active states. A `unique` index on
   `{ unitId, status: RESERVED }` that counts cancelled reservations would permanently block re-reserving
   a unit whose reservation was cancelled.
3. Deactivated master data stays resolvable from every historical record that references it.

## 10. Indexes

- Every collection declares its indexes in the change that introduces it. An index added later, after the
  collection has grown, is a production incident rather than a change.
- Compound indexes lead with the **scope anchor** (`legalEntityId`, `branchId`, `projectId`), because every
  query is scope-filtered — an index that does not support the scope filter will not be used.
- Unique indexes on: business numbers, provider IDs, provider event IDs, idempotency keys, normalized
  phone numbers where deduplication applies.
- Partial indexes for uniqueness constrained to active states (see §9).
- Index review is part of every phase gate.

## 11. Validation and schema discipline

- Mongoose schemas are `strict`. An undeclared field is rejected, not silently stored — document drift in
  a schemaless store is otherwise invisible until it breaks a report.
- Field-level validation in the schema in addition to boundary validation. Defence in depth: the worker
  and migrations write to the database without passing through the API boundary.
- Required-field and enum constraints declared in the schema, not only in application code.
- Bilingual configurable labels are always `{ ar, en }` with both required
  ([ADR-0003](../decisions/adr-0003-arabic-first-localization.md)).

## 12. Personal data

- Identity documents, contracts, and scans live in **private S3**, never in the database. The database
  stores a reference, content type, size, checksum, and uploader.
- Phone numbers are stored normalized (E.164) for deduplication, alongside the original as entered.
- Protected field classes are declared centrally so serializers, exports, and PDFs share one definition —
  see [security-model.md](security-model.md) §3.
- Test fixtures are synthetic. Production data never enters development
  ([ADR-0015](../decisions/adr-0015-secrets-and-repository-hygiene.md)).
