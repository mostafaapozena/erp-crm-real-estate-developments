# Security Model

Implements [ADR-0006](../decisions/adr-0006-server-side-authorization.md). Scope: identity, sessions,
authorization, field security, separation of duties, audit, and data protection.

Role names, permission assignments, approval thresholds, and the segregation-of-duties matrix are
**stakeholder inputs**, not design choices. They are blocked on `SD-02`. This document defines the
mechanism; the policy fills it in.

## 1. Identity

- **Accounts are linked to employee records.** A user is an employee with system access, not a free-standing
  login. This is what makes offboarding complete: suspending the employee suspends the access.
- **Personal accounts only. Shared accounts are prohibited** (gap `G-10`, Arabic scope p19). Enforced by
  policy and by the audit requirement — a shared account makes every audit record meaningless, which is
  the actual reason for the rule.
- Lifecycle: invitation → activation → active → suspended → terminated. Never deletion
  ([ADR-0009](../decisions/adr-0009-no-hard-delete.md)) — deleting a user would orphan every audit record
  and approval they ever created.
- **Passwords:** Argon2id. Never logged, never returned, never included in any export.
- **MFA is mandatory** for privileged roles: system administration, Meta administration, payroll,
  treasury, banking, and finance approval.
- **Offboarding is one atomic workflow** (gap `G-08`): suspend the account, **terminate all active sessions
  immediately**, and transfer owned customers, tasks, and pending approvals. A suspended account whose
  session is still live is not suspended.

## 2. Sessions

- Short-lived access tokens; refresh tokens rotated on use and stored in `Secure`, `HttpOnly`, `SameSite`
  cookies. Tokens are never placed in `localStorage`, where any script could read them.
- Refresh-token reuse detection: presenting a rotated token invalidates the whole session family. This is
  the standard defence against a stolen refresh token.
- Device and session listing with individual and bulk revocation.
- Server-side session invalidation on suspension, password reset, permission change, and termination —
  permission changes must take effect immediately, not at next login.

## 3. Authorization — three independent layers

All three apply on every request. Passing one does not imply the others.

### Layer 1 — Action permission

Granular verbs, not coarse roles: `view`, `create`, `edit`, `submit`, `approve`, `reject`, `publish`,
`pause`, `cancel`, `export`, `download`, `communicate`, `reassign`, `reconcile`, `post`, `reverse`.

Roles are named bundles of permissions for administrative convenience. **Authorization checks always
evaluate permissions, never role names.** A check written against a role name breaks the moment the role
composition changes.

### Layer 2 — Data scope, enforced inside the query

| Scope | Visible records |
|---|---|
| `self` | Records the actor created or owns |
| `assigned` | Records explicitly assigned to the actor |
| `team` | The actor's team |
| `department` | The actor's department |
| `branch` | The actor's branch |
| `project` | Explicitly granted projects |
| `legalEntity` | The actor's legal entity |
| `all` | Unrestricted — audited, and granted to as few accounts as possible |

**Non-negotiable rule: no repository method accepts a filter without a scope. Fetch-then-filter is
prohibited.**

Post-filtering leaks through paths that are easy to miss:

| Path | How a post-filter leaks |
|---|---|
| `count()` / pagination total | Reveals how many records exist outside the scope |
| Aggregations, sums, averages | Values include out-of-scope records |
| Exports and report generation | Frequently bypass the list endpoint entirely |
| Global search | Matches out-of-scope records and reveals their existence |
| `exists` / uniqueness checks | Reveal a record the actor may not see |

An out-of-scope record returns `404`, not `403`. A `403` confirms the record exists, which is itself a
disclosure.

### Layer 3 — Field-level restriction

Protected field classes: identity documents, salary and payroll, bank account details, balances,
commission amounts, credentials and tokens, audience definitions.

A field the actor may not see is **absent** from the response — not `null`, not masked in the client. The
server must never serialize a value the actor is not entitled to, because anything sent can be read.

Field restrictions apply identically to list responses, exports, PDFs, notifications, and search results.
Exports are the most common leak: a PDF or spreadsheet generated by a different code path than the list
endpoint will bypass field stripping unless it uses the same serializer.

## 4. Separation of duties

Distinct from permission: an actor may hold both `create` and `approve` yet still be forbidden from
approving **their own** record.

Applies to: campaign budgets, discounts, refunds, vendor bank-account changes, beneficiary/payee data
changes (gap `G-05`), payroll runs, accounting posting, and financial period opening (gap `G-04`).

- The default is that maker ≠ checker.
- An exception requires an explicit, configured, audited policy — never a code branch.
- Delegation and escalation are configured, time-bounded, and audited. A delegation must not become a
  permanent silent grant.

## 5. Audit

Append-only. Never deleted, never edited, not exempt for data cleanup
([ADR-0009](../decisions/adr-0009-no-hard-delete.md)).

Every record carries: actor, action, entity type and ID, before/after summary, reason where required,
UTC timestamp, session ID, IP address, correlation ID, and provider reference where applicable.

Audited events:

- every mutation
- every approval, rejection, delegation, and escalation
- every export and **download or print of a generated document** (gap `G-03`, Arabic scope p17)
- read access to sensitive data classes
- authentication events: login, failure, logout, password reset, MFA change, session revocation
- permission, role, and scope changes
- every provider mutation, with the provider request ID

Audit records store a **summary**, not a verbatim copy of protected values. An audit log containing
plaintext salaries or bank numbers becomes the least-protected copy of the most sensitive data.

## 6. Input validation

Every request is validated at the API boundary against the shared Zod schema from `packages/contracts/`
before authorization or business logic. Unvalidated input never reaches a query, an adapter, or a
document generator.

- Reject unknown fields rather than ignoring them — silently ignoring an unknown field makes a
  client-side mistake invisible and can mask a mass-assignment attempt.
- Mass assignment is structurally impossible: mutations accept only explicitly declared fields.
- Upload validation covers size, declared type, actual content type, and a malware scanning hook.
- File downloads use short-lived signed URLs to private S3. Objects are never public.

## 7. Transport, storage, and operational controls

| Control | Requirement |
|---|---|
| Transport | TLS everywhere. HSTS. Helmet security headers. Strict CORS allow-list. |
| CSRF | Protected where cookie-based authentication applies |
| Rate limiting | Per IP and per account, on authentication, export, and provider-triggering endpoints |
| Secrets | AWS Secrets Manager in deployed environments; environment variables locally. Never in code, never committed ([ADR-0015](../decisions/adr-0015-secrets-and-repository-hygiene.md)) |
| Encryption at rest | Database and S3 encryption; provider tokens encrypted with KMS-managed keys |
| Files | Private S3 only; signed, expiring URLs |
| Log redaction | Configured once at the Pino instance — tokens, passwords, authorization headers, cookies, bank, salary, and identity fields |
| Dependency scanning | In CI; no unresolved critical or high finding passes a gate |
| Backups | Periodic, with **restore testing** — an untested backup is not a backup. Policy blocked on `SD-18` |

## 8. Required tests

A phase gate does not pass without these, per endpoint:

1. Action denied without the permission.
2. Out-of-scope records absent from results **and from counts and aggregates**.
3. Protected fields absent for unauthorized actors — including in exports and PDFs.
4. Self-approval rejected where separation of duties applies.
5. Audit record written for every mutation, export, and download.
6. Privilege escalation attempts fail: editing one's own roles or scopes, assigning a permission the actor
   does not hold, acting on another actor's behalf.
7. Session invalidated immediately on suspension and on permission change.
8. Unknown and malformed input rejected, not coerced.
